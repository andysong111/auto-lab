# PlayJolt Owner Loop

The owner has two operating responsibilities:

1. submit an original idea or name a popular game to study;
2. decide `APPROVE`, `REJECT` or `ENGINE_ADVICE` from one evidence packet.

PlayJolt owns normalization, originality boundaries, design, construction, QA, bounded repair, Preview, release evidence, marketing production, scheduling, measurement and learning. Missing evidence stops the system before an external side effect.

## One approval packet

The system presents one compact packet containing a playable Preview, measured comparison, provider cost and repair ledger, release status and marketing preview. Approval scopes are explicit. A future packet can combine game acceptance, Production release and organic marketing publication so the owner makes one informed approval rather than several operational decisions.

An early taste-baseline approval does not imply a later Production approval. Halo Guard V9 was approved before RC evidence existed, so it may enter marketing asset preparation but cannot be released or posted yet.

## Idea intake

`OWNER_IDEA` may be free-form. `POPULAR_GAME_REFERENCE` must include a fresh source URL, transferable abstract principles and the complete copy boundary from `policy.json`. The system creates an original game identity contract; it never copies names, characters, narrative, art, audio, assets, layouts, source code, store copy, screenshots or a distinctive ruleset.

## External side effects

Organic publication requires the scoped owner approval plus an exact-source RC packet, live game URL, marketing file QA, connected accounts and hosted-copy verification. Paid advertising never starts automatically. Credentials, new paid commitments, legal decisions and account reconnection remain exception boundaries.
