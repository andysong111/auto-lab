# PlayJolt Universal Game Engine

## Decision

Halo Guard V9 is the owner-approved taste baseline. Its durable state is `SELECTED_FOR_INTEGRATION`, so paid intake stays stopped while PlayJolt evolves from whole-game generation into a constrained game compiler whose trusted components improve after every measured attempt.

This document adapts the proven architecture of AI-Saurus without copying its commerce-specific implementation. AI-Saurus succeeds across unlike products because it separates variable source facts from stable production machinery: source normalization, a universal identity contract, conditional rule modules, fixed output roles, golden cases, staged promotion, bounded retry, quality gates, accepted-cost measurement and permanent regression learning. PlayJolt needs the same separation for games.

## Core model

```text
owner taste + market evidence + prior learning
  -> normalized game brief
  -> Play Identity Contract
  -> reviewed component selection
  -> protected mechanic runtime + generated presentation
  -> deterministic assembly and zero-paid preflight
  -> browser play QA + commercial QA
  -> RC or terminal rejection
  -> component-level learning and regression coverage
```

AI may propose and compose. It must not silently redefine the mechanic authority, score, progression, lifecycle, budget, safety boundary or release source.

## Seven layers

### 1. Normalized game brief

Convert every idea into one typed contract before construction:

- target player and session length;
- primary gesture and first-action clarity;
- skill loop, success, recoverable warning and real failure;
- stage depth and difficulty curve;
- visual world, character roles and camera language;
- feedback, audio, mobile and accessibility requirements;
- originality boundary and benchmark principles;
- cost, provider, repair and Production limits.

Unknown or contradictory fields fail closed before a provider call.

### 2. Play Identity Contract

This is the game equivalent of AI-Saurus's universal product identity contract. It records what must remain true across every skin, model response and repair:

- mechanic family and authoritative runtime;
- exact input-to-action map;
- collision and scoring authority;
- progression, completion, failure and replay lifecycle;
- required player, friendly, enemy and goal roles;
- camera, readability and interaction-depth invariants;
- deterministic Oracle traces and expected state transitions.

For Halo Guard, radial pointer defense, readable interception, forgiving early pressure, visible guardian state, rescue/enemy distinction, terminal failure and immediate replay are identity invariants. Names, scenery and cosmetic themes are not.

### 3. Reviewed component registry

Build versioned components instead of asking a model to recreate every system:

- mechanic runtimes;
- input adapters;
- score/progress and lifecycle controllers;
- difficulty curves;
- character rigs and behavior roles;
- camera and environment kits;
- motion, impact, audio and result-feedback kits;
- mobile HUD and accessibility shells;
- telemetry and exact-source release adapters.

Each component declares compatibility, parameters, diagnostics, tests, performance budget and known failure codes. A candidate may use only reviewed combinations.

### 4. Rule modules

Conditional modules add rules only when the brief needs them. Examples include one-thumb control, reflex timing, chain reaction, physics launch, collection, survival pressure, character readability, low-end mobile, reduced motion and short-session replay.

Rules must produce executable constraints and tests, not prompt prose. Conflicting modules are rejected before construction.

### 5. Game compiler

The compiler assembles a candidate from the identity contract and reviewed components. AI owns bounded creative fields such as theme, original character styling, environment dressing, copy, particles and animation parameters. Factory-owned code retains mechanic state, score, input parity, lifecycle, replay, diagnostics and release provenance.

Repairs target the failing component or parameter. They do not rewrite unrelated systems or reset the candidate budget.

### 6. Golden play bank and staged promotion

Halo Guard V9 becomes the first owner-approved golden play case. Preserve deterministic play traces, screenshots, performance limits and owner taste notes.

Promotion stages:

1. Stage 0, zero-paid proof: contract validation, Oracle traces, input parity, lifecycle, performance bounds and component compatibility.
2. Stage 1, protected vertical slice: one complete 60-second loop with real browser evidence on desktop and mobile.
3. Stage 2, full candidate: Technical, Product and Commercial QA plus comparison with the golden bank.
4. Stage 3, RC Preview: immutable source, isolated RC branch, Factory CI, exact-source Preview, byte identity and SHA-256 release packet.
5. Stage 4, Production: separate current owner approval, controlled release and rollback proof.

No earlier stage can authorize a later one.

### 7. Learning and economics

Measure accepted game cost rather than raw generation cost:

```text
accepted game cost =
  (provider cost + QA cost + repair cost + owner review cost)
  / probability of an owner-acceptable, gate-passing result
```

Every terminal failure maps to a component, invariant and permanent regression test when testable. Track whether a fix reduces the same measured failure on later candidates. Retire components and families that repeatedly fail; never disguise them with a new ID.

## Controlled variation policy

The next experiments should not be unrelated full games. Change one major dimension at a time around the approved baseline:

1. keep the core loop and test a stronger difficulty curve;
2. keep mechanics and test a new original character/world kit;
3. keep both and test progression or reward depth;
4. only then test a distinct mechanic family through a new zero-paid taste prototype.

This makes outcomes attributable. If mechanic, art, controls, progression and economy all change together, a rejection teaches almost nothing.

## Owner involvement

Owner input is required at three narrow boundaries:

- approve a new taste baseline after zero-paid prototypes;
- review the best measured weekly candidate when evidence suggests a real improvement;
- explicitly approve Production after an RC release packet is complete.

The owner should not repair candidates, tune prompts or repeatedly judge obviously weak outputs. The Factory should stop before spending when reviewed components or evidence are missing.

## Immediate implementation sequence

1. Materialize Halo Guard V9 as a golden play contract with deterministic traces and visual evidence.
2. Extract its mechanic, character-role, environment, camera, feedback and mobile-shell components into versioned registries.
3. Add a compatibility compiler and fail-closed preflight for component combinations.
4. Change sequence 38 construction to vary one reviewed axis while inheriting the golden invariants, then move the policy to `SELECTED`.
5. Add component-level failure attribution and trend reporting.
6. Run at most one paid candidate per UTC day; pause after two measured regressions.
7. Promote only a measured improvement through the existing RC Preview and release-packet path.

Production remains unauthorized until a fresh explicit owner decision.
